## 4. Sucessos

- **Review adversarial 3-camadas foi load-bearing.** Resgatou a 3.2 (incompleta) e a 3.4 (não-consumível). Sem ele, o Epic 3 shipava quebrado. É o porquê de 259/259 ser real, não cosmético.
- **3.3 provou o padrão:** story pequena com escopo fechado passa limpo no review. O contraste com a 3.2 é a evidência.
- **Deferred-work governado:** cada item com severidade + gatilho de reativação ("reavaliar ao tocar X"). O `[Med]` é decisão documentada (D1), dívida gerenciada.
- **Framework method-agnostic + instalável** entregue ponta-a-ponta — FR-17/18, AD-2/AD-7 satisfeitos.

---

## 5. Desafios

1. **3.2 `done` sem ACs cumpridas nem registro preenchido.** Gate entre "implementei" e `done` inexistente. A confiança ficou toda no review — funciona, mas é caro e frágil depender do review pra detectar *incompletude*.
2. **3.4 false-green no boundary npm.** Testes verdes deram confiança falsa porque nunca exercitaram `npm install` num projeto consumidor. Faltou o smoke `npm pack → install em temp → process-ai --help`.
3. **Doc-vs-code drift (3.1 + 3.5).** Docs/claims escritos contra realidade de dev-time, não de consumo. Mesma raiz em ambos.
4. **Spec internamente tensionada (3.1).** AC1–AC3 (enforce shape) colidiam com AC4 (não quebrar existente). Resolvido por defer (D1), mas é padrão recorrente.

---

## 6. Insights-chave

- **Dependência única do review adversarial é cara e frágil** → precisa de gates automáticos *antes* do review (self-check de ACs + smoke de distribuição).
- **"Teste verde" não é evidência fora do boundary exercitado.** Cobertura na raiz do repo ≠ produto funcionando no consumidor.
- **Claims de doc/contract devem ser validadas contra consumo real**, não assertion. Doc que cita código é testável.
- **Strictness-vs-compat** é um fork de design que vai se repetir; pertence a story dedicada que audita payloads antes de endurecer.
